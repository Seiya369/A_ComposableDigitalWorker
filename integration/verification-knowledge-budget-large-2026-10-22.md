## 分词与候选策略

计数采用开发依赖 `tiktoken@1.0.22` 的 `o200k_base` 参考编码，包含完整序列化知识信封、引用、定位、恢复导航及其自计数字段。它精确对应这一编码，**没有验证等于 GPT-6、DeepSeek 或实际 DSH 员工模型的 tokenizer**。另一套官方 Python `tiktoken==0.12.0` 对 7 类样本的数量和 token ID 哈希全部一致，见[交叉验证](../artifacts/knowledge-budget-large-2026-10-22/tokenizer/cross-check.json)。开发分词库未进入插件运行包。

K=1000；三档不是原有字节预算的同名重标：

| 候选 | 日常目标 / 软触发 / 硬限 | C 目标 / 最大 | B 单次 / 建议在场 | A 单次 / 建议在场 |
| --- | --- | --- | --- | --- |
| tight | 6000 / 9000 / 12000 | 2000 / 3000 | 3000 / 8000 | 2000 / 4000 |
| target | 32000 / 48000 / 64000 | 4000 / 8000 | 8000 / 48000 | 4000 / 16000 |
| roomy | 64000 / 80000 / 96000 | 4000 / 8000 | 8000 / 72000 | 4000 / 24000 |

A/B 可在共享硬限内借用空间；必要证据不受建议分层在场数强制淘汰。C 固定占额。软触发只收拢可选、过期和重复正文，保留版本定位；当前阶段必需证据超过日常目标时继续保留，硬限不足则原子拒绝新增包、保留既有状态并明确阶段移交。这里没有用 LLM 重写 A/B 原文，不是摘要语义保真的测试。

候选硬限还受输出预留后窗口的 20% 和实际其他输入后的剩余空间约束。64K 模型预留 8K 输出时，知识硬限缩至 11.2K。大型数据比较使用明确的 1,000,000 测试窗口与 16,000 输出预留以隔离三档容量，不声称答题模型拥有该窗口。

## 结论和未验证部分

32/48/64K 可以作为较大窗口员工的下一阶段候选，32K 是工作目标而非必需证据上限；96K 只证明某些原子任务需要更多空间，不证明所有员工应默认扩大。须先得到目标模型可信计数能力，再接入实际运行并做自主检索、多阶段交接和真实任务验收。

本轮还发现移交信封缺少被拒包的完整 `id/version/range` 清单。离线 run trace 保存了该包，但固定快照中的模型不能凭空补出所有未接纳版本；正式接入前应将未完成游标、已核验阶段结论、其证据范围及待接纳版本账本一并提供。真实运行另有默认 `maxTreeTokens=120000` 的任务树累计调用用量预算；它与单次 ABC 在场额度、模型窗口是不同限制。重复调用的输入/输出及子任务用量会累计，不能因单次知识可容纳 64K 就声称长任务能持续运行；正式接入需联测累计用量策略。

此次大型任务的 B/C 和检索路线是作者预先编排的，不能证明当前管理员能自动把大型 A 高质量编纂为 B/C。当前编纂器仍有输入字节与生成长度限制；应先实现可恢复的主题分批编纂、稳定概念 ID、逐命题证据、独立语义核验与失效传播。具体规则见[员工知识政策设计稿](../docs/architecture/employee-knowledge-policy.md)，其中已实现与待实现逐项分开。
