# 可组装数字员工 · DeepSeek Harness 插件

通过全局模板、项目员工实例和对话框 `@`，为 Harness 项目配置可复用的数字员工。首个内置员工是“技术负责人（架构师）”，属于“软件开发团”。

## 本地运行

需要 Node.js 22.19+ 或 24+、pnpm，以及应用了[通用工作区扩展补丁](integration/README.md)并完成构建的 DeepSeek Harness **0.1.1-rc.2**。默认使用相邻的 `../deepseek-harness`；其他位置通过 `DSH_SOURCE_PATH` 指定。当前兼容基线为 `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`。

```sh
npm ci --legacy-peer-deps
npm run setup
npm run build
npm run service:start
```

macOS 使用 `service:start` 启动独立后台服务，终端或本次任务结束后仍可访问。`npm run service:status` 检查服务，`npm run service:stop` 正常停止，日志在 `.local/service`。这是当前登录会话内的服务，不配置登录自启；注销或重启电脑后重新执行启动命令。开发时或其他系统使用 `npm start` 在独立终端前台运行，并保持该终端打开。

打开 http://127.0.0.1:3080 。启动脚本首次在 `.local/harness` 建立单独的 Harness profile（后续启动保留安装、卸载和配置状态），在 `.local/workforce.json` 保存员工数据，并为本项目创建软件开发团的架构师实例。存在原 Harness 设置时，复用其模型设置与凭据服务引用；没有模型凭据时，请在 Harness 的模型设置中配置。插件不保存 API key，也不会模拟模型回答。

`WORKFORCE_PORT` 可修改监听端口；`WORKFORCE_HOME` 可修改本地演示 profile 的位置。开发依赖链接脚本只修改本插件的 `node_modules`；它不修改 Harness 源码。

首次从仓库恢复项目时，可按[干净环境安装步骤](integration/README.md#从源码仓库恢复)准备固定版本的宿主并应用补丁。源码、依赖锁文件、三个岗位技能、宿主补丁和构建/启动脚本均纳入版本管理。`node_modules`、`lib` 和安装包通过安装及构建生成；`.local` 中的本机配置、员工实例、记忆、会话和凭据引用保留在本地，换机迁移时另行备份恢复，不随 Git 提交。

## 使用

界面跟随 Harness 的浅色、深色与系统主题，字号和控件尺寸沿用宿主设置页，详见[界面样式约定](docs/ui-style.md)。

1. 点击“工作区”标题附近的员工图标，打开全局模板库。点击团队名称展开或收起成员，右侧显示组织架构图。左侧员工可拖到其他员工前后调整同级排序、拖到员工中间设为其下级、拖到团名设为顶层；下属随员工整体移动，松开后自动保存并同步组织图。搜索中或当前配置尚未保存时暂停拖拽。点击左侧员工或图中的员工节点，直接进入七模块岗位配置页。页面顶部同一行可设置员工名称、所属团队、所属层级和所属上级，先选择层级，再从同团的上一层员工中选择上级。“添加员工”也直接打开岗位配置页；从团队进入时默认加入该团，未加入团队的模板列在“未分组员工”中。新建团队时先保存团队名称与简介，再添加员工。
2. 未配置团队时，点击项目文件夹右侧 `… → 配置团队`，单选团队名称后确认，一次加入全部员工和工作流副本，并映射到项目员工实例。岗位草稿以待启用状态加入。配置后菜单改为“查看团队”和“取消团队”：前者直接打开项目团队；后者解除该项目的团队配置、停用成员并停止相关任务与流程，保留项目配置、记忆和历史。取消后菜单恢复为“配置团队”，重新选择同一团队会恢复原实例及原来的启用状态，不重复创建或自动重跑旧任务。
3. 在该项目对话输入框行首输入 `@`，选择一个已启用的员工，再描述任务。提交后进入原生员工执行会话。
4. 项目配置中的任务页可提交任务、查看输出与交付物、取消执行、验收或退回成果。新任务仍通过 `@` 或任务页提交。
5. 在项目的“工作流”页编辑流程，填写本次目标后发起。查看每步交付，验收通过后进入下一步；可暂停后续步骤、恢复、退回修改、重试或取消。
6. 在记忆页确认并维护项目共享记忆或员工项目记忆。记忆有来源和版本，不会随模板进入其他项目。

首版每条 `@` 消息只有一位主办员工。多人协作通过主办员工的授权委派工具进行。输入中间的 `@` 仍交给 Harness 原有的文件等引用来源。

全局图标编辑可复用模板；项目入口先选团队，再进入项目团队查看成员、工作流和岗位配置。员工与工作流在同一次原子事务中创建，检查团队和岗位模板版本；任一步失败都不会留下部分团队。同一团队在不同项目拥有独立的员工、工作流 ID 和员工记忆。“配置团队”每次单选一个团队，添加其他团队时保留已有项目成员，不执行隐式替换或删除。

团队的顶层员工为第 1 级，无需选择上级；其他层级的上级候选仅包含同团中紧邻上一层的员工，并排除自己和所有下属。层级选项从第 1 级延伸到可选上级的最深层级加一级。切换层级会清除不匹配的上级，非顶层员工需选好上级才能保存。在岗位配置页点击“保存配置”，一次保存岗位模块与团队归属、汇报关系；返回团队后，组织图按保存的关系自动排列，调整员工层级与上级会同时移动其下属子树，下属层级随组织关系更新。团队名称与简介仍在团队设置中通过“保存团队”保存。模板与团队关系的修改不会覆盖已有项目员工实例。

岗位配置页不再单独显示右侧设置栏。保存时，满足岗位使命、工作职责和验收标准等校验的员工自动成为可用模板；尚未完成的配置保留为草稿。

项目与来源团队之间保存唯一安装记录；响应丢失、重复点击或服务重启后重试，都返回原有团队实例。未归属于已配置团队的既有员工，在岗位唯一且匹配无歧义时纳入新团队，保留 ID、项目权限、岗位配置和记忆；多实例或重复岗位不自动猜测对应关系。团队模板之后的修改不覆盖已经创建的项目副本。

团队页通过顶部“组织架构 / 工作流”页签切换，切换保留尚未保存的团队配置。“工作流”页签支持定义顺序流程：流程名称、步骤名称、负责员工、步骤任务，以及输入要求、交付要求、验收条件、每步超时和尝试次数上限。配置项目团队时复制全部定义，并映射为项目员工 ID。项目的“工作流”页可继续编辑或新增流程；点击“发起”才开始执行，配置团队本身不触发任务。无工作流的旧团队按空列表处理。

每次发起冻结项目流程版本，每个步骤复用现有 Harness 员工执行器，保留独立会话和任务尝试。前序交付通过人工验收后，才向下一位员工传递已验收摘要和有权读取的产物引用，不传其他员工私有记忆。流程的组织方式和岗位的工具权限分别管理；改变流程不能扩大员工权限。首版支持顺序流程，不包含并行分支、条件路由、定时触发或自动验收。运行契约与恢复规则见[工作流架构](docs/architecture/workflows.md)。

## 架构师的七个模块

| 模块 | 默认配置 |
| --- | --- |
| 岗位职责 | 现状与需求分析、架构设计、技术决策、工作包拆解和技术评审 |
| 能力组合 | 内置架构分析、架构设计、技术评审三个技能，以及受控文件、记忆与委派工具 |
| 模型配置 | 继承当前项目来源会话或 Harness 默认模型，也可在员工配置中指定 |
| 知识与记忆 | 架构工作方法、证据标准、项目共享记忆和员工在该项目的记忆 |
| 权限 | 读取常见项目说明、构建清单、src/tests/scripts/docs；只向 docs/architecture 新建交付物 |
| 协作规则 | 最多两层委派，初始无下属授权；添加真实员工并配置允许模板后可委派 |
| 交付标准 | 明确目标、约束、接口、数据与权限边界、失败恢复、实施计划和验证局限；交付后待用户验收 |

架构师没有 shell 或网络工具；岗位指令无法扩大权限。工具执行同时检查启动快照与当前授权。文件工具不跟随符号链接，写入只创建新文件；修订现有方案时使用新的版本文件名。

首版提供上述三个内置技能及受控 `worker_*` 工具。配置任意 ID 不会安装新的技能、工具或外部连接器；网页知识来源只保存引用，不自动抓取网页。Shell、网络和自动验收目前未提供执行适配，界面会明确显示。后续扩展位置及对象关系见 [基座架构说明](docs/architecture/foundation.md)。

## 数据与运行

员工模板、团队模板、项目实例、项目记忆、任务记录相互独立。实例保存模板版本的完整快照，模板编辑不会覆盖项目配置。项目员工身份不等于 session ID，每次任务对应独立的原生 Agent 会话。

同一员工的任务串行执行。运行有步数、时间、团队任务数和 token 限额。任务结束先进入“待验收”，经明确验收后才成功。宿主重启把曾经执行但结果不确定的任务标为失败并保留记录，不自动重做可能已产生副作用的操作。工作流中已登记但尚未执行的任务可恢复派发，已验收步骤不会重复执行；失败步骤经人工检查后通过“重试当前步骤”生成新尝试。独立员工任务通过新的工作单重试。

完成的原生员工会话保留可见，便于查看和刷新后的历史恢复；继续工作通过 `@` 提交新的工作单，以便重新装配当前配置、记忆和预算。

存储使用原子文件替换、写入队列、排他锁和版本冲突检查。若宿主被强制终止时遗留 `workforce.json.lock`，确认没有员工服务进程后才能清理该锁。运行一个服务实例，浏览器可多开；各编辑器通过版本号防止覆盖其他窗口的修改。

## 源码位置

```text
src/domain/       七模块、模板、项目实例、记忆、工作单、持久化
src/workflow/     流程定义、原子状态转换、交接、执行接口与调度
src/harness/      Cordis 宿主插件、原生 Agent 执行、权限工具、技能注册
src/ui/           中文模板/项目配置界面与七模块表单
src/client/       原生侧栏、弹窗、@ 输入与 HTTP 接入
skills/           架构师三个可查看和修改的技能文件
scripts/          构建、Harness 链接与本地启动
integration/      通用宿主接口补丁、兼容检查、安装与卸载说明
tests/            领域、输入路由和真实 Harness 执行循环测试
```

## 验证与分发

```sh
npm run typecheck
npm test
npm run build
npm pack
```

启动本地服务后，可执行 `node tests/ui/workforce.e2e.mjs` 验证原生配置界面，或 `node tests/ui/mention.e2e.mjs` 验证 `@` 选择。设置 `WORKFORCE_LIVE_MODEL=1` 后运行后者，会发出一次实际模型请求，并检查身份、权限、会话跳转和完成后的历史恢复。

`node tests/ui/project-staffing.e2e.mjs` 使用独立临时 Harness 和两个临时项目，验证原生“配置团队”入口、团队单选、工作流编辑、整队创建、旧员工与记忆保留、重复配置及跨项目隔离，不发送模型请求。浏览器测试需要已安装的 Playwright 浏览器；使用 `WORKFORCE_FIXTURE_ONLY=1` 可只启动临时服务，再通过浏览器手动验收。测试退出时清理临时数据。

工作流浏览器验收可执行 `WORKFORCE_FIXTURE_ONLY=1 WORKFORCE_WORKFLOW_FIXTURE=1 node tests/ui/project-staffing.e2e.mjs`，打开输出的临时地址。这个测试环境额外加载离线模型插件，预置两位员工和两步流程，可实际完成发起、验收、退回、重试与恢复；目标含 `TEST_SLOW` 时会等待，便于验证取消。生产安装包不包含这个离线插件。

构建产物是同时包含 Host 和 Client 两面的独立 npm 安装包。插件通过正式的工作区插槽追加入口，不复制、不替换宿主工作区组件。宿主需要先具备本项目补充的两个通用插槽；具体兼容基线、补丁及安装命令见 [integration/README.md](integration/README.md)。构建脚本只读取本插件与已安装的公开依赖，不再读取 Harness 私有源码。

本地演示可在停止服务后执行 `npm run plugin:uninstall` 或 `npm run plugin:install`，随后重新启动并刷新页面。卸载保留员工实例、权限、项目记忆和文件。`npm run test:lifecycle` 用真实安装包在临时环境验证安装、卸载和重装恢复，详见[验证记录](integration/verification.md)。
