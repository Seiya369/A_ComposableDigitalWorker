# 项目任务组织与工作界面研究

研究日期：2026-10-19。基线：本仓库插件 0.3.2、已验证的官方 DSH 0.2.1-alpha.2。本文是设计建议，尚未成为实施决策；不表示新增能力已经上线。

**建议采用：以项目目标、任务和成果对象组织工作，用依赖与里程碑协调执行，在具体任务内允许智能体动态分析；界面采用项目工作台，按需切换 Graph，并保留原生会话入口。**

**先区分三个问题。**

| 维度 | 回答的问题 | 对本项目的建议 |
| --- | --- | --- |
| 领域建模 | 系统管理哪些有身份、状态、版本的东西？ | 项目、人员、任务、成果、验收与依赖 |
| 工作编排 | 谁在什么条件下做什么，完成后如何交接？ | 标准流程与受控动态规划组合 |
| 界面呈现 | 用户怎样理解进展、处理异常、检查成果？ | 工作台、列表、关系图、详情和会话各负其责 |

工作流并不等同于结构化分析法；面向对象也不自动意味着灵活协作。采用对象模型的系统可以执行固定流程，固定流程中的每项任务也可以由智能体灵活调查。后台使用图结构，同样不要求用户必须画图才能工作。

如果“对象”指产品经理、架构师、研究员等人员，解决的是能力分工。如果“对象”指需求、设计、接口、页面、报告、数据集等工作对象，就能进一步管理项目完成所需的状态和证据。一个工作对象可以由多人接力完成，一个人也可以参与多个对象；不需要给每个对象创建常驻智能体。

**当前代码已经具备的基础与缺口。**

| 部分 | 已有实现 | 本轮发现的缺口 |
| --- | --- | --- |
| 人员与团队 | 稳定 ID、模板来源版本、项目独立配置快照、汇报关系 | 岗位配置成熟度高于项目执行总览 |
| 工作单 | 负责人、执行状态、会话、输出、产物、验收、用量 | 工作目标与一次执行尝试尚未独立建模 |
| 工作流 | 顺序步骤、冻结运行定义、每步人工验收、暂停/恢复/取消/重试 | 无并行汇合、条件路由、跨步骤返工和计划修订 |
| 成果 | 工作单下的标题、路径/内容与媒体类型 | 无独立成果版本、需求追溯、验证证据关联及下游过期判定 |
| 界面 | 模板库、人员/团队配置、任务详情、记忆、工作流运行记录、组织树 | 无统一的目标、待办、阻塞、验收和成果工作台 |
| 执行能力 | 六个受限 `worker_*` 工具及本插件技能映射 | 尚未打通通用 Bash、Web 及任意已安装 DSH Skill 的选择与执行 |

核对依据：[`src/domain/types.ts`](../../src/domain/types.ts) 的 `ProjectEmployee`、`RunArtifact`、`WorkforceRun`；[`src/workflow/repository.ts`](../../src/workflow/repository.ts) 的 `actions/advance/control`；[`src/harness/runtime.ts`](../../src/harness/runtime.ts) 的工具限制与技能加载；[`src/ui/WorkforceWorkspace.tsx`](../../src/ui/WorkforceWorkspace.tsx)、[`src/ui/ProjectPanels.tsx`](../../src/ui/ProjectPanels.tsx)、[`src/ui/TeamOrgChart.tsx`](../../src/ui/TeamOrgChart.tsx)。

这些缺口不会通过把顺序列表画成节点连线而自动消失。当前模型、工具、权限和工作流行为未在本轮研究中改变。

**任务组织方式的取舍。**

| 方式 | 优势 | 局限 | 建议用途 |
| --- | --- | --- | --- |
| 预先固定步骤 | 易复用、核查和追踪，交接明确 | 对未知子任务、需求变化和跨步骤返工适应较弱 | 数据处理、固定报告、例行检查等稳定工作 |
| 人员自由协作 | 易探索和临时分工 | 容易出现责任不清、重复工作、信息漂移和缺少完成证据 | 临时咨询、短期探索、小任务 |
| 工作对象与成果状态驱动，结合流程 | 能围绕成果分工，保留依赖、评审与变更影响 | 需要任务、成果、依赖与验收的统一状态模型 | 研究、设计、开发等完整项目的主架构 |

Anthropic 将预定路径与动态智能体区分，分别讨论动态分解、并行任务和评估反馈循环。OMG CMMN 则以变化中的资料和关系组织知识型工作，明确与传统流程建模互补；IBM 的成果中心建模研究也将业务实体生命周期与功能流程组合。上述资料支持组合设计的思路，不能直接证明某个具体插件配置的完成率更高。[Anthropic](https://www.anthropic.com/engineering/building-effective-agents)、[OMG CMMN](https://www.omg.org/cmmn/index.htm)、[IBM Research](https://research.ibm.com/publications/declarative-business-artifact-centric-modeling-of-decision-and-knowledge-intensive-business-processes)。

**建议的最小工作模型。**

1. 项目保存目标、范围、必交成果和完成标准。通用模板提供初始角色、成果要求和常用流程，项目实例保存实际进展。
2. 任务保存目标、负责人、必要输入、预期成果、验收标准、前置依赖和状态。执行尝试独立记录；重试、换人和返工不丢失原始任务身份。
3. 成果拥有稳定 ID 与版本，关联生产任务、负责人、文件/内容和验证证据。只有针对具体版本的验收才有效。
4. 标准工作流产生初始任务与依赖。负责人可以依据新事实提出新增、拆分、调整或取消任务，并记录计划修订及原因。
5. 调度器依据已提交状态决定哪些任务可执行；模型负责提出计划和完成任务，持久化状态决定计划是否生效。绘图坐标仅是显示数据。
6. 人员交接传任务目标、必要事实、相关成果版本和已确认结论。沿用权限过滤，不自动共享全部聊天或个人记忆。
7. 明确成果和任务依赖后，再加入独立任务并行；共享文件、接口和外部操作需要先协调冲突和执行归属。

计划依赖可以采用无环结构；返工通过新的任务、成果修订和执行尝试表示，保留历史。确需循环的流程则必须定义明确状态转换与退出条件，不能把带环工作随意称作 DAG。

例如开发“用户注册”功能：先形成需求与接口约定；前端、后端和测试设计可以围绕已确认接口并行工作。联调发现接口不一致时，创建修订任务，保留接口 v1 与 v2 的差异。依赖旧接口的实现、测试显示“需要重新验证”，相关人员只返工受影响部分。项目结束由必交成果及验证是否满足完成标准决定，单个模型输出“已完成”不能替代验收。

默认每个小任务都要求人工点击，会形成新的瓶颈。后续可按项目约定让有可靠自动检查的常规步骤自动推进，关键成果与里程碑由负责人验收；自动检查、评审意见和人工决定都需绑定具体成果版本。这是建议，当前实现仍是每步人工验收。

动态任务应有并发、时间、尝试与成本边界，发现没有进展时调整计划或升级处理。Microsoft Magentic-One 用任务与进展记录区分高层计划和当前派工，提供了这方面的参考；这里不要求引入其运行时。[Microsoft Research](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)。

**工作界面按用户动作选择呈现方式。**

| 用户要完成的动作 | 优先界面 |
| --- | --- |
| 配置人员岗位、模型、Skills、权限 | 人员表单 |
| 找待办、阻塞、验收和最近成果 | 项目工作台与列表/看板 |
| 了解人员汇报关系 | 团队组织树 |
| 追查任务为何不能开始、会影响哪些后续任务 | 任务依赖图 |
| 从需求追到设计、实现、测试和报告 | 工作对象/成果关系图 |
| 解释需求、补充资料、检查工具调用 | DSH 原生会话 |

DSH 继续提供模型与工具配置、原生会话、项目文件归属和主题外壳。`graph_horses` 的模板范围继续作为配置库；项目范围默认进入工作台，提供任务、成果、流程、团队与资料的导航。

建议的宽屏布局：

```text
项目：用户注册功能          目标 / 当前阶段 / 阻塞 / 待验收
┌──────────┬──────────────────────────┬─────────────────┐
│ 工作总览 │ 列表 / 看板 / 依赖图      │ 所选任务或成果  │
│ 任务     │                          │ 负责人 / 状态   │
│ 成果     │ 需要我处理               │ 输入 / 交付要求 │
│ 流程     │ 执行中与阻塞             │ 依赖 / 成果版本 │
│ 团队     │ 待验收与最近成果         │ 验收 / 返工     │
│ 资料记忆 │                          │ 打开执行会话    │
└──────────┴──────────────────────────┴─────────────────┘
```

小屏使用列表与可切换详情，不强制同时显示三栏。工作台应优先回答：目标是什么、进展到哪、哪里卡住、下一步谁做、已经交付什么。

Graph 分成三种视图：团队图的边表示汇报关系；任务图的边表示前置依赖；成果图的边表示实现、验证、引用或派生。人员可作为任务节点字段或泳道，消息留在事件与会话中。默认不把全部人员、文件、任务和消息叠成一张网。

Graph 的主要价值是阅读关系、路径和影响范围。图可读性研究显示，不同呈现对不同任务、规模和密度的效果不同；不应把任意节点阈值直接用作本产品标准。[Ghoniem、Fekete、Castagliola](https://www-sop.inria.fr/orion/COGC/teams/INSITUghoniem-fivj05-final.pdf)。本项目默认工作台、按需关系图的选择，是结合用户动作作出的产品判断。

必要交互包括：自动排版与稳定位置，搜索定位，聚焦上游/下游，折叠阶段，按负责人/状态筛选；节点只放名称、负责人、状态和关键阻塞，长内容放详情。列表与 Graph 必须读取同一份状态、提交同一套命令，切换视图保留选择和筛选。

新增依赖、更换负责人、调整顺序等操作应同时支持菜单或表单，不强制拖拽；状态同时用文字与图标表达。W3C 对拖动功能要求提供无需拖动的单指针替代操作，键盘可操作性另行满足。[WCAG 2.2：Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements)。

工作台显示可核验的动作、输入、结果、证据与决策。界面的进度、错误和纠正入口要与实际执行状态一致。Microsoft HAX 提供了能力说明、纠正、反馈和控制等交互设计依据。[HAX Design Library](https://www.microsoft.com/en-us/haxtoolkit/library/)。

**遵守当前官方插件边界。**

已核验的官方 alpha.2 接口支持 root `main` keyed slot、`sidebar.panellist`、`layout.selectPanel` 与 `uiWorkspace.openSession`。现有 [`src/client/index.tsx`](../../src/client/index.tsx) 已使用这些机制；工作台与 Graph 可以在插件自身面板内实现。

官方依据位于本机已验证发行版的以下包内 README：`@deepseek-ai/dsh-client-ui-layout/README.zh.md`、`@deepseek-ai/dsh-client-ui-sidebar/README.zh.md`、`@deepseek-ai/dsh-client-ui-workspace/README.zh.md`。

插件详情栏可以展示自己的任务、成果和验收信息，通过官方导航打开原生会话。现有核验不能支持任意嵌入原生聊天组件的承诺；会话专属右栏也不能直接当成全局面板的通用插槽。实现仍遵守 ADR-001，不补宿主接口、不替换组件。

**建议的实施顺序与验证方法。**

1. 先让项目工作台集中显示目标、待处理事项、任务状态与成果，复用现有任务详情和原生会话导航。
2. 补足实际执行能力，按官方公开机制接入已讨论的默认工具和个人 Skills；界面必须显示真实可用状态。
3. 将稳定任务、成果版本、验证与验收记录明确建模，再加入依赖、变更影响和局部返工。
4. 对已有依赖提供 Graph 阅读与定位，随后逐步增加并行、条件和受控计划调整。
5. 保留标准流程模板与 JSON 交换；增加字段和实体前先设计版本迁移与兼容，布局偏好不作为执行真相。

建议用四类代表项目比较方案：固定报告、开放研究、小功能开发、需求中途变化。固定输入、人员能力、模型和预算，记录按验收标准计算的项目完成率、人工干预次数、返工范围、耗时和 Token 用量。界面实验可复用同一份执行记录，单独比较找阻塞、追踪成果、处理验收的时间和错误率，避免把模型差异误认为界面收益。

拟定用户任务：进入一个 30 任务、6 人的项目，10 秒内找到待本人验收和阻塞；三次操作内找到失败原因、负责人和受影响任务；从需求找到成果与测试证据；执行“退回—修改—重提—验收”保留历史；切换会话再返回不丢定位；无拖拽与窄屏仍可操作。以上是未来验收目标，本轮没有进行这些产品实验。

本轮仅新增本文档，完成代码、官方本地文档和外部一手资料核对；没有修改执行器、工作流、用户配置、宿主或安装包，也没有开展模型质量对比测试。
