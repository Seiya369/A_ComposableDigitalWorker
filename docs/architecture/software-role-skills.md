# 软件开发岗位技能

本插件随包提供22项可供模型调用的技能，通过官方 `ctx.skills.register` 发布，目录基于真实前言描述。前言标识与目录不一致、内容缺失、YAML损坏或禁止模型调用时拒绝加载。技能正文只在使用时读取，必备技能每份工作单加载一次，优先技能匹配任务时通过原生技能工具加载。

这些是为当前DSH团队工作流独立编写的简洁岗位方法，不要求Codex专有工具、另一套多代理调度或工单系统。保持岗位、任务授权与原生策略边界；没有复制或修改用户全局Skill。技能资源只保存一份，员工配置只引用稳定ID。配置不会因技能存在而自动授予权限或安装MCP。

## 六岗位配置

预设源文件：`skills/software-development-presets.json`。全新 profile 的默认六岗位直接消费该预设源，由 `src/domain/software-defaults.ts` 生成完整岗位、认知与记忆规范、软件开发团和一条软件工程工作流。新功能开发与缺陷修复共用这条完整流程，不再附带独立的“缺陷修复”默认流程。安装不自动执行业务任务，普通升级和状态重开不静默重置用户配置。

团队默认由产品负责人统筹需求、范围、优先级和用户验收，技术负责人/架构师、UX/UI设计师、测试负责人和运维负责人平级、独立地向产品负责人汇报，只有开发人员向技术负责人/架构师汇报。设计、质量与运行就绪结论保持专业独立，不能由开发或架构代为豁免。层级来自团队的实际 `reportsTo` 关系，不通过岗位名称推测，也不因层级提高原生权限。

| 层级 | 岗位 | 直接上级 |
|---|---|---|
| 1 | 产品负责人 | 团队负责人，无上级 |
| 2 | 技术负责人/架构师 | 产品负责人 |
| 2 | UX/UI设计师 | 产品负责人 |
| 3 | 开发人员 | 技术负责人/架构师 |
| 2 | 测试负责人 | 产品负责人 |
| 2 | 运维负责人 | 产品负责人 |

| 岗位 | 必备 | 优先 |
|---|---|---|
| 产品负责人 | requirements-acceptance | grill-with-docs、to-spec |
| 技术负责人/架构师 | architecture-design | architecture-analysis、to-tickets、code-review、technical-review、retro、worktree-cleanup |
| UX/UI设计师 | ux-design-review | frontend-ui-engineering、design-system-guidance |
| 开发人员 | incremental-implementation | test-driven-development、debugging-and-error-recovery、pr、worktree-cleanup |
| 测试负责人 | quality-verification | code-review、webapp-testing、worktree-cleanup |
| 运维负责人 | release-readiness | shipping-and-launch、ci-cd-and-automation、worktree-cleanup |

技术负责人审查生产实现、架构及边界；测试负责人交叉审查测试断言、需求覆盖、契约和遗漏风险，复用相同版本及已有评审证据。代码审查与实际测试执行分别记录，不以阅读代码宣称通过。`pr` 只整理说明稿；`retro` 在阶段结束或重复问题时提供工程改进建议，与插件认知记忆的经验归档不同。没有装入会自行调度整套团队的 `implement-spec`。`design-system-guidance` 是轻量设计规范指导，不冒充包含上游 `ui-ux-pro-max` 的数据与搜索程序。

## 一条完整的软件工程流程

工作流团队快照采用上述六岗位及同一层级。步骤负责人通过稳定成员 ID 绑定；保留原有十个稳定步骤 ID，并在用户验收后增加独立的授权发布步骤，共十一步；避免以重新编号或新建员工替代已有身份。

| 步骤 | 负责人 | 关键交付 | 不合格退回 |
|---|---|---|---|
| 1. 需求澄清与验收基线 | 产品负责人 | 需求、范围、优先级、验收条件；缺陷影响和复现要求 | 本步骤 |
| 2. 交互与体验设计 | UX/UI设计师 | 关键路径、界面状态、响应式与可访问性规范 | 本步骤 |
| 3. 技术方案与根因分析 | 技术负责人/架构师 | 接口契约、ADR、实施工作包；适用时提供已验证根因和修复边界 | 本步骤 |
| 4. 测试计划与回归基线 | 测试负责人 | 功能、性能与风险矩阵；适用时保留修复前失败基线 | 本步骤 |
| 5. 增量实现与缺陷修复 | 开发人员 | 实际改动、回归测试和开发验证记录 | 本步骤 |
| 6. 独立代码与契约审查 | 技术负责人/架构师 | 真实差异审查、问题及修正依据 | 第5步 |
| 7. 独立功能、性能与体验复测 | 测试负责人 | 原问题、关联路径、体验与性能复测证据 | 第5步 |
| 8. 候选版本与运行就绪 | 运维负责人 | 候选归档、哈希、许可、生命周期验证、监测及回滚演练；本步不发布 | 本步骤 |
| 9. 用户验收与发布决定 | 产品负责人 | 需求覆盖、独立质量和运行就绪证据、用户验收与发布决定 | 第5步 |
| 10. 授权发布与运行核验 | 运维负责人 | 当前授权范围内的真实发布及运行验证，或范围外不适用说明与制品交接 | 第8步 |
| 11. 工程复盘与知识交接 | 技术负责人/架构师 | 根因、跨职能改进意见、知识交接与资源收尾 | 本步骤 |

每一步均包含输入、输出、验收标准、负责人和返工目标。测试负责人独立给出质量结论，并复用设计师的真实体验检查与运维的目标环境证据；产品负责人可以将残余风险与选项呈交用户决定，但不得把失败或未执行检查改称通过。非界面、性能等不适用项需要任务相关的理由，不能为走流程虚构交付。

固定退回目标只是默认返工路径：包装或环境问题在运维就绪阶段修正，普通实现缺陷返回实现；真正的范围与验收条件变化由产品负责人显式重定需求基线，不能每次小问题都从需求重做。技术复盘的后续优先级交由产品负责人安排。

候选准备、用户验收和实际发布分成不同阶段。第8步只准备制品和演练；第9步记录用户验收与发布决定，不能自动授予 DSH 权限；第10步必须有用户对当前目标、范围及动作的明确授权，并服从 DSH 原生权限与审批后才能执行。发布超出任务范围时记录不适用理由并交接制品；任务要求发布但尚未授权时保持待办，不能声称完成。真实发布后需核验运行情况，失败保全证据并按已授权方案恢复。

缺陷修复沿“复现与根因 → 最小修复 → 独立审查 → 功能与性能回归 → 候选版本 → 用户决定 → 授权发布或交接”闭环，不以新增一份演示工作流代替验证与授权。

## 随包专业认知与已有安装更新

六岗位各带一份明确概念、定义和关系的专业参考资料；团队描述也包含协作及知识交接定义。资料由 `src/knowledge/software-knowledge.ts` 统一维护，知识图谱逐条引用这些原始定义并持久保存。它们是专业参考，不代表任何用户项目已经执行、通过测试或形成了确认记忆。

已有安装通过显式默认内容更新计划处理，普通 `WorkforceStore.open` 不做重置。计划只整体替换与已知旧版原始内容完全匹配的团队及主工作流，追加尚不存在的随包专业资料，保留所有现有或自定义资料。已修改、被其他团队采用的缺陷流程保留其定义与历史。操作前应停止目标宿主并核对只读计划。

已采用但尚未执行、未自定义的主工作流，可以在同一事务内更新到新团队与步骤定义：保留六名项目员工的 ID、模块配置、原生会话选择、当前稳定步骤 ID、确认记忆和历史，仅同步实际汇报关系及定义版本。任何执行记录、交付完成记录或采用后的职责、人员、层级、步骤改动都会使默认替换跳过并报告原因；不强行改写已有成果。具体操作与归档要求以[接入指南](../../integration/README.md)为准。

## 工作树必须收尾

不为每份任务强制创建工作树。确需隔离时，记录本任务归属、路径、创建提交及集成目标，停止临时进程；合并并核验后必须清理物理checkout、允许清除的可再生依赖构建物及其专属Git管理记录。收尾失败列出路径、原因和保全状态，不能把仅合并提交报告成完整收尾。

`worktree-cleanup` 的零依赖Node工具位于它自己的资源目录，只接受明确的主仓库、单个临时路径、任务owner和本地集成分支。`create` 实际创建工作树并记录归属，不接受事后认领；`audit` 只读；`cleanup` 复核祖先合并关系及干净状态后调用原生 `git worktree remove`，不使用force或批量prune。详细参数以技能及helper `--help` 为准。

未合并提交、tracked/staged修改、未跟踪或未声明ignored文件、隐藏索引标志、锁定、主树、他人目录、越界符号链接及嵌套/裸Git仓库都会阻断清理。只有创建时明确登记为可重新生成、整体ignored且不含用户成果的允许依赖构建根目录才被移除。默认保护ignored内容；不扫描删除旧工作树。Squash/cherry-pick不能仅由祖先关系证明已合并时，先保全并核验成果，再明确处理，不重置HEAD伪造核验。临时分支及共享Git历史不在清理范围。

平台管理的工作树使用原平台归属与移除入口，不能绕过平台直接删除。卸载插件只停止技能注册及插件工作，保留用户仓库和未收尾工作树；这些目录仍属于用户成果，不能随插件完全清理而盲删。

## 安装与验证

技能与脚本随npm包安装，升级后重启/刷新DSH，从能力组合目录选用；卸载后注册和插件入口停止，不遗留全局技能副本。兼容版本、安装和完全清理见安装说明。

隔离Git行为测试证明允许的工作树物理路径、列表项及专属管理目录均消失，同时阻断有独占数据的目标；官方原生技能注册测试覆盖22项模型可调用、六岗位引用、资源定位及插件卸载后其他技能仍存在。实包官方临时profile检验安装和卸载，实际六人修改通过原有API版本校验，不启动真实模型任务。
