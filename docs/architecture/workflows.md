# 顺序工作流执行契约

范围：独立岗位工作流模板、团队成员流程快照、项目流程副本、每次运行记录、步骤员工任务。独立模板与交换协议见 [graph_horses 契约](graph-horses.md)。复用已有 Harness 员工执行器，不新增另一套模型、权限或记忆服务。

## 模块与依赖

- `workflow/types`：数据和持久化 / 执行器接口。
- `workflow/repository`：原子状态转换、快照、幂等命令、步骤与员工任务同时落盘。
- `workflow/engine`：观察已提交状态，调度已登记任务，不自行调用模型。
- `harness/runtime`：实现执行接口，复用模型、技能、权限、记忆和子 Agent 限制。
- 项目工作流界面：配置、发起、验收、暂停恢复、取消与重试；不承担状态机职责。

## 行为约定

1. 顺序执行。工作流定义和版本在发起时冻结；修改模板或项目流程不会改写运行记录。
2. 每步绑定本项目员工。调度时快照岗位，执行期间继续核对有效权限。
3. 步骤任务与工作流尝试在同一事务中创建。执行器仅启动这个任务 ID，重复通知不会创建新任务。
4. 每步完成后由项目负责人在界面验收，通过后继续。退回必须填写意见，重试创建新尝试并保留旧记录。数字员工可作为评审步骤提供意见，首版人工决定验收。
5. 暂停阻止后续步骤，当前已登记的员工任务可完成。恢复不重做已验收步骤。取消停止当前任务和子任务，不启动后续步骤。
6. 重启可启动尚未执行的已登记任务；曾经进入执行但结果不确定的步骤转为待处理，人工检查后重试，不自动重放外部副作用。
7. 交接只传已验收摘要和经过接收员工权限过滤的产物引用；不传完整对话或其他员工私有记忆。流程不能提升员工权限。交接上下文有长度上限。
8. 每个步骤有超时，每个流程有尝试次数上限。第一版失败重试由用户发起，不做不受控自动重试。
9. 开始请求和控制命令有幂等标识；控制命令包含运行版本，验收绑定具体任务尝试，防止陈旧页面误验收。

## 持久化与验证边界

首版沿用单宿主本地 JSON 原子存储，不宣称分布式调度或外部副作用 exactly-once。持久化端口可替换为事务数据库；调度器和界面无需随数据库实现改变。异常退出留下存储锁时继续采用存储的显式冲突处理，避免抢占仍在写入的实例。

完整状态在读取和提交时校验：项目归属、步骤顺序、任务双向引用、尝试次数、配置版本和验收状态必须一致。事务失败不更新内存、不留下部分磁盘状态；提交后的通知只唤醒调度，不携带另一份可变状态。大规模历史归档、多实例调度和故障转移需要先替换本地存储并增加租约，不应启动多个写入实例共用该文件。

## 接口与扩展点

所有写入复用宿主同源 `/digital-workers/api/command`，正文为 `{ action, payload }`。

| 操作 | 关键字段 | 冲突处理 |
| --- | --- | --- |
| `workflow.save` | `projectId`、`projectTeamId`、`workflow`、`expectedVersion` | 新建版本为 0；已有定义必须匹配当前版本 |
| `workflow.start` | 项目、团队和流程 ID、`workflowVersion`、`request`、`requestId` | 同请求 ID 和内容返回原运行；改变内容拒绝 |
| `workflow.control` | 项目和运行 ID、`action`、`commandId`、`expectedVersion` | 过期版本返回 409；重放相同命令不重复执行 |

控制动作包括 `pause`、`resume`、`cancel`、`retry`、`review`。验收必须附当前尝试的 `runId` 与 `decision`；退回必须附 `note`。任务的普通验收入口拒绝工作流步骤，流程状态与验收结果必须一起提交。返回的运行 ID、步骤 ID、尝试任务 ID 和原生会话 ID 互相独立，可用于追踪一次交接。

模板和项目共用 `WorkflowForm` 及 `workflow/definition` 校验器。调度器只依赖 `WorkflowPersistence` 与 `WorkflowExecutor`；时间和 ID 生成可注入仓储测试。新增执行后端应实现已登记任务启动、取消两项接口；新增流程类型应扩展状态机和一致性测试，不把条件判断放进页面事件。

配置范围：每条流程 1–50 步，每步最多 1–10 次尝试，超时 100 毫秒至 1 小时（表单最小 1 秒，实际还受宿主任务超时限制）。输入、交付和验收要求各最多 20 项、每项 2,000 字符。交接摘要预算 24,000 字符，序列化交接资料预算 32,000 字符；被截断的摘要有标记，不假装完整上下文。运行日志保留最近 300 条事件，每步全部尝试另行保留。

当前 Harness 接入基线已升级到 `0.2.1-alpha.2`，执行器回归仍覆盖以下行为；新版升级证据见 [验证记录](../../integration/verification.md)。

## 2026-09-09 历史验收

2026-09-09，在隔离的临时 Harness 和两个临时项目中，通过浏览器完成项目流程编辑、发起、退回、暂停时重试、恢复、两步验收完成、运行日志展开及执行中取消。检查磁盘/API 确認项目修改不覆盖模板，第二步仅在第一步验收后派发，返工与交接内容保留，取消不会派发后续步骤。浅色和深色均使用宿主主题变量。

HTTP 检查还覆盖重复发起不增建任务、陈旧控制返回 409、跨项目控制拒绝、普通任务验收入口无法绕过流程。测试模型只注册在临时 profile 中，生产代码没有模拟输出或测试模型后备。临时环境启动方法见 README。

框架依据：本地锁定的 Harness `0.1.1-rc.2` Agent / Tools / Session 源码；React `18.3.1` 采用受控表单和 effect 清理；Node `22.19+` 文件句柄同步。参考 https://react.dev/reference/react/useEffect 和 https://nodejs.org/docs/latest-v22.x/api/fs.html#filehandlesync 。

自动化验证包括：状态转换、跨项目拒绝、幂等请求、重复调度、验收阻断、退回与重试、权限过滤、超时、取消竞争、重启恢复、失效员工、错误配置与引用的整笔回滚，以及真实 Harness 执行器和离线模型。
