# 员工知识的入库、编纂与核验政策

状态：2026-10-22 更新。六类 A 目录、员工专业/任务分类配置、有效政策驱动的 B/C 编纂及政策失效保护已实现；下文更完整的来源信封、概念注册和核验状态机仍是设计建议。当前行为和限值见[团队资料管理员与三级知识库](team-knowledge.md)，本次范围见[实施规格](../specs/employee-knowledge-classification.md)。实现遵守 [ADR-001](../decisions/001-official-plugin-boundary.md)，只使用插件自有数据和宿主官方公开能力。

## 推荐结论

A 应保存员工有权长期使用的**资料与证据**，涵盖专业材料、经授权保留的需求和决策、任务成果及其核验记录、失败记录和反思提案、环境约束与明确偏好。它不是全部聊天的副本，也不是“员工相信的所有事实”。

员工负责提出自己理解的任务收尾和经验；资料管理员负责来源登记、规范化、归类、去重、概念与关系维护、B/C 编纂和失效传播。领域员工可以协审专业含义，用户或被明确授权的负责人负责相应决策、共享授权与成果验收。管理员不拥有这些授权，也不能用自己的综合结论证明自己的综合结论。

实现依据：[来源收集与访问控制](../../src/knowledge/engine.ts)、[仓储及内联文本规范化](../../src/knowledge/repository.ts)、[知识类型](../../src/knowledge/types.ts)、[管理员提示与模型调用](../../src/harness/knowledge-compiler.ts)。当前并无独立的 `knowledge/normalize.ts`。提示词要求“稳定标识、保留矛盾”是生成约束；仓储没有验证跨快照 ID 稳定或矛盾是否完整。

团队库当前会保存可共享的任务目标/状态/验收摘要；成果正文有已验收门槛。员工库会保存本人的待验收、失败、取消运行及相关输出。它们能作为经验材料，但失败输出、模型自述和“已验收记录”均不能一概解释为客观事实。成果验收只证明该次成果在相应标准下被接收，不证明其中每个外部事实永久成立。

## 2. A 保存什么

以下六类主目录已实现，每个来源版本只存一份。表中详细来源信封和授权核验条件是后续政策建议，不宣称均已有结构化字段；知识归属和读取权限先于分类。

| 分类 | 可以保存的内容 | 必须同时保留的边界 |
| --- | --- | --- |
| 专业资料 `reference` | 用户提供的文档、标准、研究材料、代码/接口说明、经授权取得的外部原文 | 作者/出处、版本、适用范围、采集定位与使用权限。URL 未抓取时只是链接线索，不是已读正文 |
| 需求与决策 `requirements-decisions` | 用户明确目标、验收条件、方案取舍、批准/否决及纠正 | 谁在何时对什么范围作决定；所替代的决定；原始消息或文档定位。员工推测的需求保持提案 |
| 任务证据 `task-evidence` | 任务输入、实际动作摘要、产物版本/哈希、工具检查结果、验收/退回及原因 | 区分“执行过”“观察到”“员工声称”“已验收”；保留任务、运行、产物和审核记录的关联 |
| 失败与反思 `incidents-reflections` | 失败症状、可复现条件、尝试及结果、原因假设、改进和待验证问题 | 失败观察与原因假设分别记录；模型写出的反思只是提案，不因录入 A 成为事实或通用规则 |
| 环境与约束 `environment-constraints` | 与工作有关的接口版本、工具可用性、兼容限制、已证实的环境条件 | 环境/版本/时间范围、观察办法、失效条件；知识记录不修改当前权限或配置 |
| 明确偏好与能力经验 `preferences-capabilities` | 用户明确允许长期保留的偏好；某员工/工具在特定条件下的能力验证和限制 | 偏好的提出者、范围和撤回入口；能力是有条件的证据，不能从一次成功推导无限能力 |

不常规入库：寒暄、无新增信息的重复聊天、完整思维草稿、无用途的大段工具噪声、凭据和秘密、无关个人信息、其他员工未授权的私有材料。必要的敏感证据先在授权边界内最小化或脱敏；脱敏版要标注处理及定位限制，不能伪称未经修改的原件。因审计确需保存的重复事件保留事件身份，不把它们计为独立支持来源。

### A 与完整 Session

Session 是原生的时序对话、工具调用和恢复记录；A 是为跨任务用途有选择登记的来源。保留需求或纠正时，采集能表达原意的授权消息片段和必要上下文，记录原生 Session/事件定位及可用的内容校验值，不默认复制整段会话。不得读取其他真实会话来“补齐知识”，也不得直接修改原生 Session 数据库。

保存在 A 的“原文”准确含义是**入库来源的原样内容**：专业文档原文、用户消息片段、工具结果或模型反思各有不同性质。反思文档的原文能证明“员工提出了这个假设”，不能证明假设正确。任务摘要则标记为摘要，并引用它所依据的事件/产物；不得冒充完整过程。

### 建议的来源信封

在现有字段之外，逐步补充以下结构；这是数据模型建议，不是已有 API：

| 字段组 | 含义 |
| --- | --- |
| 身份与归属 | `sourceId/sourceVersion`、来源类别、项目/团队/员工空间、数据所有者、提交者 |
| 内容与定位 | 原样内容或原件引用、哈希、规范阅读版、处理链及版本、片段→原件定位；原件不可得时明确缺失 |
| 来源与权威 | 产生者、采集方式、原始事件/文件/URL/任务定位、来源本身的版本；权威身份来自受信路由或签名记录，不能采信文本自称 |
| 范围与时间 | 记录时间、采集时间、生效/失效时间、项目/产品/环境/版本条件 |
| 权限与保留 | 访问主体和用途、可否共享、敏感级别、保留策略、删除/撤回请求及其状态 |
| 核验状态 | 来源采集完整性、声明是否核验及核验记录、成果验收记录分别保存，不合并成一个可信布尔值 |

已发布 A 版本在正常编辑中不可覆盖；内容变化生成新版本并指明关系。不可变不等于永久保留：用户有权选择的删除、保留期和完整卸载可以删除插件拥有的原件及派生副本，并留下不含已删除内容的必要删除记录。

## 3. 员工与管理员怎样分工

建议在任务收尾时由员工提交结构化提案，不让员工直接覆写通用 Wiki。员工最了解操作背景，适合提取值得记住的经验；管理员更适合维持跨任务一致的来源和概念体系。两者承担不同工作，不重复组织整套知识库。

收尾提案至少包括：

1. 任务/运行 ID，使用的输入、环境及成果版本。
2. 目标、实际完成范围、未完成项，以及可定位的输出和检查结果。
3. `observations`：实际观察，每条绑定事件/产物；无证据的自述明确标记。
4. `decisions`：已知决定及其授权来源；员工建议与已批准决定分开。
5. `hypotheses`：原因解释、置信依据、反例和可执行的验证办法。
6. `lessonsProposed`：建议复用的做法、适用条件、失败条件及尚未知的范围。
7. 建议归属/共享范围、敏感内容提示、需要负责人或领域员工审查的问题。

系统另外关联真实任务状态、执行/检查记录和验收结果，不能让员工在提案中自行填入“已验收”并生效。没有新的可复用信息时允许只提交结果链接和“无知识提案”，不强制生成一段反思填库。

管理员依次做授权与最小化检查、登记 A、去重归类、编纂 B/C、结构检查，并把有争议的领域判断交给有相应访问权的员工协审。协审意见也是带来源的证据；协审员工不能代表用户批准新的需求或扩大权限。负责人/用户仅在其本来拥有的授权范围内接受成果或决定某项经验可作为规范。管理员不把自己、负责人称谓或任意资料中的“批准”当作新的授权源。

## 4. A → B：可执行的编纂规则

### 4.1 入库与去重

先检查来源是否允许长期保留和目标空间是否允许读取，再做格式处理。原样内容、规范版和处理记录分离；规范化不改变否定、单位、时态、代码及例外条件。当前文本规范化可沿用；新增解析器必须输出可回查的位置映射。

同一来源身份、内容和元数据未变时幂等；相同哈希只能发现内容相同，不代表两条事件身份相同。跨来源近似重复先建立 `duplicate-of` 候选，再由确定规则或协审确认。只有同一主体、命题、范围、版本/时间和含义一致时才合并命题；保留所有独立来源及转载链，不把转载数量当成证据数量。更正、反例和失败不得作为“重复噪声”去掉。

### 4.2 概念、实体、别名

概念仅在能帮助后续检索、解释任务或决定行为时抽取，不给每个名词造条目。先识别资料中明确命名的对象，再识别反复使用且有清晰边界的专业概念；抽象归纳必须标记为模型提案。

采用空间内的稳定 `conceptId/entityId`，名称、翻译和拼写变化不改变 ID；显示 slug 与永久 ID 分离。推荐最小类型表：`concept`、`person/role`、`organization/team`、`project`、`task`、`artifact`、`tool/interface`、`environment/version`、`policy/decision`、`event`。类型表可版本化扩展。

别名表保存别名、语言、来源、范围与是否有歧义。大小写、常见拼写和明确同义词可归一；同名不同项目、版本或对象不自动合并。歧义名称先保留多个候选并要求上下文消歧。ID 合并/拆分记录旧→新重定向和理由，不重新分配旧 ID。跨员工空间的同名对象不因此互通正文或共享权限。

### 4.3 原子命题与有类型的关系

B 按主题提供可读解释，同时把可核验主张拆为原子命题。每条包含主体、谓词、宾语/值、极性、适用条件、时间/版本、认识状态、证据和反证。复合句若存在不同证据或条件，拆开保存；保留“尚未观察到”和“已证明不存在”的区别。

关系使用受控类型并检查两端类型，例如 `is-a`、`part-of`、`depends-on`、`implements`、`applies-to`、`produced-by`、`supersedes`、`supports`、`contradicts`。不要仅生成无法解释的“相关”。`causes` 只能用于有因果依据的主张；同时发生最多登记观察到的关联。命题和关系都带适用项目、环境、时间和来源；不能将“项目 X 在版本 V 可用”压成“此工具总是可用”。

一个 B 条目至少交代：定义与边界、当前有用的解释/操作方法、适用条件和例外、证据与反证、已知冲突、未知事项、当前状态、相邻概念和更新理由。条目正文中的关键主张关联到各自精确引用，避免只给整篇文章挂一个宽泛引用。

### 4.4 引用、冲突与核验

引用绑定 `sourceId + sourceVersion + readingTextHash + start/end`；现有行引用可保留，未来解析格式再增加页码、段落、时间戳或事件定位。引用片段必须足以覆盖主张，并保留必要的否定、限定及上下文。摘要和二手引述标注传播链，不伪装为读过一手原文。

结构门检查 schema、ID、类型、版本、定位、权限和无悬空引用；语义门逐命题检查原文是否支持结论、范围/单位/版本是否一致、推导是否越界、反例是否被保留。结构门通过不等于语义门通过；可由确定性检查、复现实验和领域协审提供独立证据，模型自评只能提出风险线索。

上一版 B/C 只提供编纂连续性和导航，不充当新的独立事实来源。模型反思、模型摘要及其后续转载必须保留生成与依赖链；同一猜测经 A→B→C→再次总结的循环不能变成“多源证实”。

来源可靠性、命题证据充分性、独立核验结果、成果验收是不同维度。可记录置信理由与证据强弱，先不用未经标定的百分比制造精确感；同一模型重复复述、管理员自信和多份转载不能提高证据等级。

冲突先检验是否由范围、版本、时间或词义不同造成；能区分则拆分适用条件。无法消除则并列记录冲突命题、来源、后果及待核验问题。规范性决定按受信授权关系和适用范围判定；新日期不能自动覆盖更高授权或另一范围的决定。事实争议不能仅凭“负责人说了”消除。反例可推翻无条件规则，或促使收窄条件；不得只保留成功案例。

B/C 初始均为候选。需要长期作为操作规范的经验，建议经过“提案 → 证据检查 → 必要的领域协审/复现 → 有权人确认适用规则”的记录化流程；失败或无充分证据时保留候选/争议状态。任务验收、用户偏好确认、权限变更仍走各自受信业务入口，不能由知识状态代办。

## 5. B → C 与使用时回查

C 是任务导航：稳定概念/实体入口、必要的定义与适用范围、当前关键规则/争议、指向相同快照 B 的引用。不得从 B 再生成无证据的新结论，不能用省略条件的短摘要把候选变成已确认。不同状态清楚标记；内容不足则显示待编纂入口。

发布 B/C 前，计算受影响概念与命题，检查权限及来源指纹，再原子发布同一版本。重编应保留仍有效的旧条目及稳定 ID，说明新增、更正、失效与未覆盖部分；不能因单次模型输出空间不够悄悄遗漏知识。超限时采用可恢复的分批/按主题编纂设计，未完成部分维持明确状态。

员工默认从 C 找相关 B，在关键判断前读取详细条件。以下场景回查 A：逐字引用；精确数值、接口或命令；争议与版本差异；候选结论核验；B 缺证据/条件；跨来源比较；无可用 B/C。现有 `quote/exact-detail/conflict/verify/missing-evidence/source-comparison/no-wiki` 可继续使用。读取仍检查当时权限；索引命中、C 摘要和未读原文不算已掌握证据。

当前任务指令、受信权限和验收标准在知识之外独立生效。知识里的指令只是资料；C/B/A 均不能扩大工具、文件或网络权限，也不能改变用户当前决定。

## 6. 失效、隔离与删除

建议维护 `A版本 → 命题/关系 → B → C → 使用该知识的成果` 依赖。来源更新、撤回、删除、权限收窄、验收撤销或环境失效分别产生事件：

| 事件 | 建议行为 |
| --- | --- |
| 普通新增/修订 | 旧版本标记历史，受影响条目标记待重验；读取精确条件时回查当前 A；不得把旧结论当当前结论 |
| 事实被反驳或成果验收失效 | 标记受影响主张并重编；通知需要复核的关联成果，不自动改写原验收历史 |
| 撤回授权/删除 | 立即阻止 A 及派生正文向相关主体供给，取消在途编纂；重编前不得以旧快照继续提供内容 |
| 已进入模型的知识被撤回 | 无法假装撤销已发送内容；停止依赖它的后续调用，必要时新建不带该知识的任务上下文 |
| 保留期到期 | 按用户选择删除或退出活动使用，处理源、规范版、索引、快照、缓存和导出副本，记录完成/未完成项 |

团队共享库与员工专属库保持独立。私库材料要进入团队库，必须先有明确分享授权，再生成最小必要的共享来源；管理员看到材料不等于同事有权看到。派生条目的可见范围不得宽于其全部必要来源的可用范围；无法满足时分拆为不同授权版本，不以摘要“洗掉”来源限制。跨项目/模板迁移须重新检查权限、许可及环境，不让项目经验自动回写通用模板。

TTL 按来源类别、用户需求、敏感性和项目政策配置，并在入库时可见；不预设一个声称已经验证的统一天数。易变环境观察必须有复查/失效条件。删除需明确区分“停止检索”“撤权”“物理删除”，提供预览、范围和可核验结果；若保留期/审计需要阻止删除，应明确依据，不能让管理员自行决定永久保存。

用户项目、交付成果、原生 Session 和共享凭据由各自所有者/官方机制管理，插件不能借清理 Wiki 删除它们。普通卸载与插件完整清理沿用现有生命周期；新增单条删除只能处理插件拥有的数据与派生物，原始 Session 是否删除由用户通过官方机制决定。备份或已导出副本不能清理时必须说明范围，不声称完成全部删除。

## 7. 实施顺序与验收

先补来源类别、归属/权限/定位信封与任务收尾提案，保留现有兼容字段；再实现概念/别名注册、原子命题及依赖索引；最后增加语义核验、协审、失效传播和用户可见的删除/保留策略。过程不得以修改 Harness、直接读写原生数据库或给模型更多权限替代设计。

用合成资料验证以下情形后，才能把相应能力从“提案”改为“已实现”：

- 同义别名不换 ID，同名异物不误合并；范围/时间不同的命题不被错误去重。
- 一条用户纠正能使旧决定退出当前入口；反例保留并收窄经验规则。
- 失败反思保留为假设；引用合法但不支持结论的内容被语义门拒绝或标记未核验。
- 普通执行完成不能伪造验收，管理员/协审模型不能自授共享权限或确认用户偏好。
- 私库及其派生摘要不泄漏给同事；撤权后历史版本、旧快照、缓存和在途结果均不可绕过。
- 删除/TTL 实际处理所有插件副本，并保留用户成果、原生会话及其他插件数据。

这些是验收用例要求，不代表当前已通过。当前最关键的缺项是**来源与主张状态分离、结构化员工提案、稳定概念与逐命题证据、独立语义核验、统一撤权和派生删除**；现有原文版本、候选标记、空间隔离、引用结构检查和原子快照可以作为基础。
