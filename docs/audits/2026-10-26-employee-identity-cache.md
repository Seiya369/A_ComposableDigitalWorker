# 员工身份、身份问答开销与 Chat 调用方式核查

日期：2026-10-26。基线为插件 `0.2.1 / plugin.1`、官方 DSH `0.2.1-rc.3`。本报告只保留汇总指标和通用配置，不包含用户会话正文、内部 UUID、绝对路径、凭据或原始日志。

## 结论

身份问答主动输出项目与员工 UUID，直接原因是插件把它们写进了身份首句，没有区分对用户的自我介绍与内部工具路由。界面中“数字员工”表示工作区已有独立实例，未表示常驻当前对话。两次问题实际进入两份独立交付会话，各一轮一次请求；第二份没有带入第一份问答历史。

14.2K 对“你是谁”这种身份介绍偏重。实际开销主要是完整 Agent 的系统提示、工具定义、技能目录和岗位/知识准备，而不是三个字的问题。缓存已实际生效；第二次命中率比第一次高，不能把 53% 本身当成接入故障，也不能据此认定模型只能缓存一半。

## 精确用量与口径

| 指标 | 第一份工作单 | 第二份工作单 |
| --- | ---: | ---: |
| 未缓存输入 | 13,047 | 6,543 |
| 缓存读取输入 | 896 | 7,296 |
| 缓存写入输入 | 0 | 0 |
| 全部输入 | 13,943 | 13,839 |
| 输出 | 274 | 321 |
| 总量 | 14,217 | 14,160 |
| 输入命中率 | 6.43% | 52.72% |
| 业务模型请求 | 1 | 1 |
| 实际工具执行 | 0 | 0 |

官方界面展示当前持久会话的累计值：`总量 = 未缓存输入 + 缓存读取 + 缓存写入 + 输出`；`命中率 = 缓存读取 / 全部输入`，输出不在分母中。本例每个会话只有一轮和一次业务请求，因此累计值恰好等于本次请求。`14.2K` 是取整显示，不是额外输出了 14,200 token，也不是仅未缓存部分。缓存输入仍有传输及服务商计量，不能当作零成本。

两次输入只相差 104 token，第二次的固定输入负担没有显著减少。输出计量未单独报告 reasoningTokens，不能把 321 精确拆成思考与可见回答。两次配置均为 `deepseek-v4-pro`、`max`，输出上限 8,000；该上限不是实际消耗。

## 上下文的真实构成

以下是第二份请求持久化文本及工具 schema 的 UTF-8 字节数，用于说明来源和相对体量。服务商只报告整次请求的 token 数，不能把这些字节数当作各部分的精确 token。

| 部分 | 实测大小 | 说明 |
| --- | ---: | --- |
| 工具 schema | 30,199 bytes | 35 个工具：32 个原生工具、3 个员工工具；没有实际执行工具，schema 仍随请求提供 |
| 原生系统提示 | 5,629 bytes | 两次文本相同 |
| 原生技能目录 | 10,360 bytes | 41 项目录摘要，其中 22 项来自本插件，19 项为其他可用技能；两次相同，没有重复提供第二份全量目录 |
| 运行上下文快照 | 10,165 bytes | 含目录、沙箱、审批等原生事实及 9,493 bytes 员工定义 |
| 当前时间信息 | 261 bytes | 两次时间不同 |
| 问题正文 | 9 bytes | 三个中文字；不代表整次模型输入 |

员工定义的 9,493 bytes 又包括：职责与通用规则 4,223、名册规则 148、C 知识入口 1,692、知识读取规则 1,229、交付规则 376、已载入的必备 Skill 正文 1,825。身份咨询没有实际读取 B/A，也没有委派同事；完整初始化仍将这些能力和规则提供给模型。

目录中的 22 项是摘要，不是把 22 份完整 Skill 全部展开。该产品负责人只有一份必备 Skill 正文随工作单加载；候选目录与被选中的技能正文用途不同。

原生系统、工具及目录本来就是 DSH Agent 的开销，不能把全部 13,839 输入归因于插件。插件增加岗位、所需 Skill、授权知识及员工工具；插件随包技能在原生目录中出现也是目录体量的一部分。现有记录没有相同账号/模型/时刻、卸载插件的对照请求，不能编造精确的“未安装时应少多少 token”。

## 缓存为什么没有达到接近 100%

两次配置、工具 schema、原生系统正文、技能目录、岗位职责和必备 Skill 正文完全相同。发生变化的是 C 知识入口及时间。第一份 C 有三个片段，第二份仍使用同一版本的种子知识，但新任务已归档到 A，来源指纹变化，旧 C 带上“待核验”的状态；有限包络预算下第二份只放入两个片段。实际员工库只有一份种子编纂记录，modelCalls 为 0；这不是每轮又付费整理了知识。

旧布局把动态 C 放在必备 Skill 正文和部分固定规则之前。这些稳定正文虽未变化，序列中的公共前缀却可能提前结束。两次也不是同一会话的“旧输入 + 回答 + 新问题”追加请求，而是两个全新工作单。新会话本身不会禁止服务商复用相同前缀，但不自动获得上一工作单完整追加式历史的缓存条件。

DeepSeek 当前公开规则要求匹配已经持久化的完整前缀单元。公共前缀可能要经过检测和持久化后才在后续请求中命中，缓存构建有延迟，闲置缓存会清理，命中是尽力而为。相同问题不等于完整请求相同；无法仅从本地日志判断恰好哪些前缀单元落在服务端缓存中。[官方缓存规则](https://api-docs.deepseek.com/guides/kv_cache/)

因此，本次可以证明请求并非完全相同、缓存已生效以及布局存在可改进点；不能证明具体每个未命中 token 的服务端原因，也不能保证改后某次请求必达 90% 或 100%。本机员工实例保留、进程内存、会话归档和服务商缓存是不同生命周期，删除历史不会使缓存规则更正确。

## 本次修正范围

1. 身份首句只含姓名/岗位；明确不主动输出 UUID、内部路径、版本和工具协议。内部路由资料后置，必要工具调用仍有真实 ID。用户明确技术排查只提供必要非敏感信息，凭据不能披露。旧回答不改写。这是模型表达约束，不是对任意生成内容的绝对防泄漏保证。
2. Chat 候选改为“本工作区已启用员工 / 自由职业人模板”，提示“单次委派”，选中后的输入提示明确会打开独立工作单。普通项目的工作流、主办人及调用行为不变。
3. 稳定岗位、通用规则和必备 Skill 放在变化的知识/资料之前；不移除权限、工具、必备技能、来源证据或候选状态，不篡改命中统计。
4. 真实连续输入回归额外复现了交接竞态：界面每秒轮询，交付已完成而员工执行作用域尚未释放时，下一条普通输入会被旧工作单拒绝。修复使用 DSH 官方 `ComposerBlocks`，在导航前保护独立交付输入，成功完成原生交接才开放发送；不锁原 Chat 或其他会话，原生 Stop 保留，不拦截/复制/重发用户消息。恢复失败保留可重试状态；卸载只清理本插件自己的锁。

这些修正改善表达和前缀稳定性，不声称已经把完整 Agent 变成低 token 的轻咨询入口。新增表达约束自身也占输入；是否降低真实费用及延迟，需要服务商实测，离线用量桩不能证明命中率提升。

## 常驻对话与每次显式调用

| 比较 | 明确绑定员工常驻此对话 | 每次显式 `@`（当前） |
| --- | --- | --- |
| 后续普通输入 | 继续交给绑定员工，直到切换或退出 | 使用原生助手；`@` 才新建员工工作单 |
| 多轮任务连贯性 | 可直接使用本对话历史 | 从来源对话只传本次任务和权限事实，员工自身岗位/知识仍加载；需明确提供必要背景 |
| 缓存与输入 | 同角色追加历史通常更有利于复用；历史仍会增长 | 每次承担完整 Agent 初始化输入；相同前缀仍可命中 |
| 无关问题 | 容易继续携带该岗位上下文 | 普通聊天可以避开完整员工执行路径 |
| 控制与误用 | 必须有清晰绑定名称、切换和退出入口 | 每次委派明确，需再次选择员工 |
| 员工配置与记忆 | 可以复用工作区员工实例 | 同样可以复用实例，不必反复新建员工 |

当前复用键是工作区与模板，不是会话。产品负责人创建一次后，在同一个 Chat 目录的其他对话也会出现在已启用分组，保存自己的配置及授权长期知识；这不代表它自动运行或自动接收所有对话。每次 `@` 都会打开新的交付会话。完成交付后通过官方交接释放员工执行作用域；普通后续输入使用原生助手，但原回答中的自我介绍仍可能影响模型措辞，不能只凭一句自称判断实际路由。

原生助手也可以保留该会话已选用的模型。官方 Session Controller 优先使用待选模型，否则从最后一份请求头恢复 provider/model/reasoning，再无记录才使用全局默认。因此历史交付刷新后仍显示先前的模型名，不足以证明员工常驻；验证还要检查没有员工职责/任务上下文和员工工具，且没有新增员工运行。本次不暗中把用户模型重置为旧来源默认值。

建议 Chat 保持每次显式委派；若需要持续顾问角色，再增加用户明确选择的“绑定此对话”能力，并提供可见身份和退出入口。不能由“以前 @ 过”隐式开启常驻。

## 后续优化建议及验收顺序

1. **优先减少不必要输入，而非只追命中比例。** 可提供本地“员工信息/名片”入口，直接展示姓名、职责及配置状态，不调用模型。它与会话里的开放式问题分别设计，不用关键词硬匹配假装模型回答。
2. **为轻咨询单独设计明确入口。** 只加载任务需要的岗位信息，按需取得知识与工具；能执行工程任务的完整工作单继续保留原生权限与能力。先用代表性咨询和执行任务做对照，验证不会漏掉必备技能和授权要求，再决定是否成为默认行为。
3. **用适合问题的推理档位。** 简单自我介绍通常不需要 Max；本次没有暗中降低用户模型设置。带工具的后续请求还需遵守模型要求保留必要思考历史，不能任意删掉以节省 token。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)
4. **按单请求核算。** 分开报告输入、命中、输出、编纂和重试；用冷启动、重复请求、知识变更、员工切换的矩阵评估实际费用与首字延迟，不用仅显示的百分比作为通过条件。
