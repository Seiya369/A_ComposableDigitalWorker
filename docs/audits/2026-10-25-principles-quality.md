## 问题、根因、计划及执行结果

| 优先级/问题 | 根因 | 实施及复测 |
| --- | --- | --- |
| P1 默认只有一个架构师，没有默认软件流程 | 六岗位技能预设只用于目录验证和手工配置，seed链路仍是早期单人状态；测试没有覆盖全新安装的默认业务内容 | 新增software-defaults，从同一岗位预设生成完整六岗、团队、两流程；保留原架构师稳定ID。新增回归在修复前失败，修复后与实包新状态断言通过。 |
| P1 文件清理残留空专属目录 | 只删除knowledge/state.json根，没有移除空knowledge父目录，阻止上级目录清理 | 用rmdir逐层清理已空的已知目录，绝不递归删除未知内容。覆盖状态已无、重复执行、其他状态根和未知文件保留。通过。 |
| P1 知识读取与状态事件出现长队列 | 每次状态修改扫描全库，反复克隆全部状态和重建作用域；停用库也等待全局pending。六岗放大了既有成本 | 按revision缓存内部只读快照，变更立即失效；合并事件、按plan和检查点跳过未变空间；显式flush/upload/remove仍查repository；停用库直接返回。原超时路径通过29项真实浏览器检查，权限/取消/失效/增量测试通过。 |
| P1 完全清理专属会话持久记录缺少能力 | 官方服务明确无持久删除API，删除底层文件会违反不改宿主/公开接口边界，且会威胁用户历史 | 已在安装说明与验收记录明确列为未满足项。等待上游归属删除能力；本轮没有以隐藏记录或停止会话冒充持久删除。 |
| P2 默认官方验证目录依赖不全 | 四个peer不存在，Node向上解析到外部开发依赖，旧默认路径与UI基线不统一 | 原有归属检查正确拒绝，未放宽检查；统一使用完整官方npm目录，所有peer物理归属和版本通过。 |
| P2 项目同步随所有历史放大 | 每个原生Workspace为了查询一个project都调用全量snapshot | 增加本插件store.listProjects的隔离副本读法，Host一次建立Map；不改宿主接口，不绕过锁与CAS。隔离与性能测试通过。 |
| P2 生命周期文件稳定采样误判 | 连续800ms无写入不是pending归档队列排空的证明，停机的最后归档补入新配置 | 先通过已有公开知识读取路由等待队列，再采样文件。保留停机前后和重装逐文件哈希完全一致断言。最终实包通过。 |
| P2 包内原则链接失效 | README引用AGENTS/ADR-001，但files白名单漏掉两者 | 两文档随包，包检查和生命周期断言通过。 |
| P2 缺少真实延迟测量 | 原有benchmark主要验证证据覆盖、预算及引用，没有提供延迟、并发或规模测量 | 增加隔离性能脚本与真实认证API测量，记录原始样本、分位数、负载、版本和源哈希。 |
| P2 大状态整文件持久化仍随容量增长 | 每次事务需要读/验证/复制/序列化整个JSON，并执行持久同步；这是现有本地事务边界 | 保留一致性和落盘保证；本轮移除冗余读和扫描。后续存储分区/事务迁移列为独立计划，不用取消fsync或缓存脏状态来掩盖成本。 |

实际顺序为：保留既有工作 → 基线 → 新回归证明缺口 → 默认内容/清理修复 → 实包复测暴露知识队列 → 根因修复与专项测试 → 最终全量、同包生命周期、浏览器、独立性能复测。初始工作区已有大量修改，本轮未重置、混合提交或清理这些工作。

| 全量snapshot，10员工 | 30次，152KB状态 | 0.21ms | 0.25ms |
| 全量snapshot，100员工 | 30次，947KB状态 | 1.22ms | 1.35ms |

8并发API在该小样本中的吞吐约1062次/秒；这是本机回环的固定小状态测量，不能外推真实LLM并发或生产容量。1000员工时仅查询项目目录的P95约0.002ms，避免了为查询project而复制8.90MB状态。

首次安装CLI约37.3秒，重装约11.2秒（包含包管理及其缓存/网络行为）；带插件首次启动到API可用约2.03秒，重装后约1.26秒。这与“后台知识/模型整理全部完成”不同。此前并行负载下也测得更高值，保留原始探索报告，不能用不同机器负载的轮次宣称严格加速倍数。

容量脚本进程峰值RSS约631MiB，包含合成数据构造及大量快照分配，不代表驻留服务内存或泄漏结论。12/20/30次采样用于本地诊断，没有建立生产SLO、长时间soak、真实供应商延迟或WebGL帧率结论。

## 后续修复计划与验收条件

1. **P1，上游会话归属删除能力。** 准备明确的API需求：只删除有本插件归属证据、无共享引用的原生专属会话；保留用户原生聊天和交付成果。等受支持官方版本具备能力后扩展purge，在真实员工执行并持久化后测试卸载，确认专属记录消失且共享记录哈希不变。在此之前保留未满足标记，不发布为无保留合规成品。本轮没有向外提交issue或修改宿主。
2. **P2，容量目标与事务存储。** 先确定需要支持的员工、项目、运行历史和成果体积，再用相同数据测试分页DTO、历史分区/SQLite等方案。写ADR，设计旧JSON可回滚迁移、备份、并发锁、断电恢复及完整卸载归属；与旧接口并行验证后切换。验收要求是相同负载下的延迟/内存改善，同时保持CAS、历史、隔离和恢复测试通过。本轮不将未经迁移验证的存储替换塞进修复。
3. **P2，真实模型及长期性能。** 按实际部署的provider/model和允许预算，为六岗位执行代表任务，单独评估质量、token、延迟、超时、取消和权限；进行长时间队列与内存稳态测试。当前离线测试不能替代模型质量与供应商稳定性验收。
4. **P2，持续交付门禁。** 将本轮新默认内容断言、包白名单、完整官方归属检查、同包哈希生命周期及UI检查作为每次发布必要证据；扩展其他平台/Node/DSH版本前逐一验证，不能只放宽版本号。
