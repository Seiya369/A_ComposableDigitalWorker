# 员工 ABC 知识分类与专业编纂规格

状态：用户已于 2026-10-22 确认规格、测试边界与五张任务单，实施中。日期：2026-10-22。来源：本对话的六类 A、管理员统一编纂、员工专业/任务定制 B，以及既有 ABC 政策。用户已明确忽略四端及原设备要求，交付沿用现有 Host/Web 插件。

## Problem Statement

团队与员工已拥有 A 原始资料、B 重组知识和 C 概念入口，但 A 平铺来源，没有可见的六类资料目录；B 编纂只使用统一提示，未接收员工专业、职责、任务或分类规则。即使只改变专业规则，现有快照也不会重编。用户无法按岗位定制知识组织，且历史引用、私库隔离和卸载边界不能因本次调整被破坏。

## Solution

A 在每个团队共享库和员工私库下创建并实际使用六类资料目录；来源具有一个主类别和可追溯分类依据。B 继续保存详细重组知识，以员工专业、职责、所选技能、任务范围及显式配置的知识分类规则组织，C 依照同一政策提取概念、实体、关系、综述与原则。资料管理员自动编纂，员工提交资料和经验；模型综合始终为候选，不能变成用户批准或成果验收。

## User Stories

1. 作为团队负责人，我希望每个新团队及员工库都出现六类 A 目录，以便查找来源。
2. 作为资料提供者，我希望指定资料主类别，以便专业资料、决策、任务证据和反思不会混淆。
3. 作为员工，我希望授权文件及专业文本默认归为专业资料，以便入库不依赖标题猜测。
4. 作为项目负责人，我希望任务目标及验收要求归为需求与决策，以便保留真实适用范围。
5. 作为员工，我希望任务结果、产物和检查记录保留任务证据身份，以便可回查。
6. 作为员工，我希望失败观察和反思提案按其性质归档，以便假设不会自动变成事实。
7. 作为用户，我希望环境约束和明确偏好能显式分类，以便“用户确认记忆”不被误当偏好。
8. 作为既有库用户，我希望旧资料所有版本仍可读取，以便 B 的精确引用不失效。
9. 作为既有库用户，我希望分类更改生成版本，以便旧原文、哈希和行号不被覆盖。
10. 作为岗位配置者，我希望编辑专业说明、知识分类与概念提取规则，以便财务和前端员工形成不同知识结构。
11. 作为项目人员，我希望岗位模板采用后保持独立配置，以便项目修改不回写模板。
12. 作为配置交换者，我希望导入导出完整保留合法分类规则，以便迁移不丢失定制。
13. 作为管理员，我希望实际收到员工职责、技能和任务范围，以便按专业编纂而非通用名词分类。
14. 作为员工，我希望 B 条目带稳定分类标识，以便 C 能导航到有关详细知识。
15. 作为用户，我希望同义别名归一、同名异物区分，以便概念不会错误合并。
16. 作为资料审查者，我希望定义、条件、例外、冲突及未知状态保留，以便简写不改变原意。
17. 作为岗位配置者，我希望仅变更编纂规则也会重编，以便旧政策不持续生效。
18. 作为并发任务用户，我希望旧政策晚到结果不能发布，以便 B/C 不回退。
19. 作为员工，我希望关闭资料管理员时停止新目录、迁移、归档、编纂及跨任务使用，以便开关行为保持一致。
20. 作为用户，我希望普通卸载可恢复原数据、完整清理只删除插件资料，以便宿主会话和成果不受影响。

## Implementation Decisions

- 遵守现有官方插件 ADR；不修改宿主程序，不扩充原生 Session 存储，不安装源码补丁。
- 六类主目录固定为 `01-reference`、`02-requirements-decisions`、`03-task-evidence`、`04-incidents-reflections`、`05-environment-constraints`、`06-preferences-capabilities`。目录名来自受控枚举，任何来源文本或模型输出不能成为任意文件路径。
- 一个来源版本只有一个主位置；来源 ID、版本、原文哈希和阅读版行号继续构成引用身份。标签不能让复制件成为独立证据。
- 旧库兼容需要覆盖活动、退役、孤立但已落盘的历史版本。采用可恢复、幂等、受插件写锁和路径检查保护的转换/读取策略，不覆盖原件，冲突或损坏时停止并保留证据。
- 来源主类别支持显式选择；受信任务/运行事件按确定规则归类。未知旧来源默认专业资料并保留“旧记录默认”依据；不能用自由文本推断用户偏好或批准。
- 自动归类契约：配置文本/URL/授权文件→专业资料；团队说明/共享任务目标与验收条件→需求与决策；正常运行、私有任务记录、成果修订与已验收输出→任务证据；失败或取消运行→失败与反思；无显式类别的旧确认记忆→专业资料（并非偏好）。环境与偏好通过显式来源选择进入相应类别。混合运行记录保留一份，以运行状态确定主类别；分类依据写入来源元数据。
- 岗位知识配置新增有界的专业编纂规则：专业说明、任务范围、稳定分类 ID/名称/说明、概念提取与消歧补充规则。未配置时由职责、技能和合法任务上下文构造默认政策，旧配置继续有效。
- 配置上限统一按 JS 字符串 UTF-16 长度验证：专业说明 2,000、任务范围 4,000、概念规则 8,000；最多 24 个分类，每个 ID 匹配 `[a-z][a-z0-9-]{0,63}`，名称 1–120，说明 0–2,000，不允许重复 ID 或未知配置字段。保存与导入边界一致。
- 未显式配置分类时，从岗位职责生成稳定、具专业意义的分类（最多 12 项），另保留专业基础/原则与任务经验/核验入口；空岗位使用通用默认入口。ID 独立于展示名称，显式改名不换 ID，删除或换 ID 触发重编。团队分类按成员命名空间区分同名 ID；不复制员工私有补充规则或来源正文。
- 团队政策使用共享目标与成员岗位概要，不汇入员工私库正文；员工政策来自该员工的有效实例，不能扩大授权。
- B 分类使用结构化分类 ID，与详细内容及 A 引用一起保存；B 不按 A 的来源类别简单复制。C 继续引用同一快照中的实际 B 条目。
- 概念规则要求稳定标识、别名、清晰边界、适用版本与条件；保留否定、例外、冲突和不确定性。不得让来源中的命令改变编纂规则，不以反思、旧 B/C 或转载循环构造独立证据。
- 快照保存有效编纂政策的指纹。岗位、分类或提取规则变化纳入排队签名、快照新鲜度、任务启动准备及在途取消；旧政策结果发布前再次核对，不得靠提示词自律。
- 旧政策重编失败时，任务入口降级为“C 待编纂＋授权 A 元数据索引”，默认 B 搜索/读取不继续提供旧政策知识；历史文件保留。显式历史版本回查必须区分过期状态，不能作为现行默认知识使用。
- 模型按既有负责人有效选择运行；常规编纂自动完成，保留所有综合为 candidate。新增规则不代办用户批准、共享授权、权限或成果验收。
- 存储与编纂各自有明确边界；输入过大或生成不完整时保留 A 及上一完整快照，明确报告待整理，不静默丢资料。
- 32/48/64K 仍是离线候选，本次不把参考编码冒称实际模型分词，也不悄悄切换员工默认工作集或累计调用预算。

## Testing Decisions

测试只覆盖已确认的外部边界，使用合成资料，不读取真实会话或员工库：

1. **岗位配置公开命令及导入导出**：验证六类来源选择、规则保存/校验、模板与实例分离、交换往返；不验证内部辅助函数的调用次数。
2. **知识库公开入库、版本读取、发布和文件布局契约**：验证六目录真实归档、幂等、历史定位、旧库恢复、拒绝越界路径及引用完整；文件布局是用户要求的交付行为。
3. **管理员公开编纂/任务准备边界与官方宿主**：验证实际模型输入含专业政策，规则变更触发重编、旧结果不能发布、关闭开关停止写入、普通卸载恢复和完整清理。模型调用用公开服务替身验证契约；不将它当成真实模型长期知识质量证明。

沿用现有 Node test runner、类型检查、Host/Web 构建及官方隔离 profile 生命周期。每个行为按 red → green 纵向实现，保存真实失败与通过日志。最终候选以 Standards/Spec 两个独立审查轴复核，修复后更新候选哈希和必要检查。

## Acceptance Criteria

- 六类 A 均真实存在，各类输入写入正确类别；分类不改原文或阅读坐标。
- 旧库所有版本和当前 B/C 可读；重启/并发/失败恢复不丢版本；分类或内容改变递增来源版本；历史精确引用不漂移。
- UI、公开保存命令、严格导入导出均接受合法配置、拒绝无效类别/分类 ID/过长规则及路径注入。
- 两个专业不同的员工向编纂器提供不同有效政策；显式规则实际作用于 B 分类，不只是界面字段。
- 原始来源不变而政策改变，B/C 仍重编；旧政策在途结果不得成为当前快照；任务启动不注入旧政策 C。
- 无效 B 分类、悬空/过期/越界 A 引用及无效 C→B 均拒绝发布并保留上一快照。
- 反思、失败、待验收结果及模型综合不自动升级为已批准事实；来源文本不扩大权限。
- 将结构和语义验收分开：分类 ID、候选状态、引用及政策指纹以自动测试验收；同义消歧、否定/条件保留及反思边界写入编纂规则，并以少量合成编纂样例独立复核，不把模型替身测试称为事实语义证明。
- 关闭知识库不迁移、不入库、不编纂；隔离、种子首次复制和现有开关语义不回退。
- 类型、测试、Host/Web 构建、浏览器配置往返、归档检查和官方原版临时 profile 生命周期通过，记录同一归档 SHA-256，宿主程序哈希不变。
- 本次增量与已有工作区基线分别保存；PR、CI 和合并范围如实说明历史未提交依赖，不能将旧改动自动归为本次修改。
